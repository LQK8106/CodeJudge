# CodeJudge 质量整改计划

> 依据：[QUALITY-SUMMARY.md](./QUALITY-SUMMARY.md)、[RELEASE-GATE.md](./RELEASE-GATE.md)、[DEFECTS.md](./DEFECTS.md)
> 编制日期：2026-11-16
> 范围：仅覆盖总结报告中已登记的风险与未关闭门禁项；不新增功能、不做架构重构。
> 时间口径：本计划只排优先级与依赖顺序，不承诺工期。

## 1. 整改原则

| 原则 | 说明 |
|---|---|
| 先阻断、后优化 | P0 未关闭前，不投入 P1/P2 的优化工作 |
| 一项一验收 | 每项整改必须有可执行命令 + 可观察结果，不接受“已改完”口头结论 |
| 证据回填 | 整改完成后必须更新 `RELEASE-GATE.md` 对应行的“实测/结论”，并保留命令输出 |
| 不做范围外工程 | 不引入 K8s、多活、全链路追踪；容量问题优先用“接受现状 + 明确边界”解决 |

**优先级定义**

- **P0（发布阻断）**：不完成则不得对外放行或不得开启公网入口。
- **P1（受控内测前）**：影响内测可信度或会造成数据损失。
- **P2（发布后迭代）**：不阻断发布，但需排期关闭。

## 3. P0 整改项（发布阻断）

### M1 · 生产凭据重新生成并验证 fail-closed

**对应**：R1、门禁 D1、A9

**动作**
1. 逐项生成强随机值：JWT 签名密钥（≥ 32 字节）、数据库口令、Redis 口令、RocketMQ 访问凭证、监控组件口令；禁止复用本地 `.env` 中的任何旧值。
2. 只写入目标环境的密钥管理位置或运行时注入，**不写入仓库**；确认 `.env` 仍被忽略。
3. 将本地验收环境的旧凭据视为已泄露，重建相关容器与数据卷（仅验收环境）。
4. 关闭 2 项硬编码 WARN：按 `docs/LAUNCH-CHECKLIST.md` A1 的清单逐项确认默认值已被显式配置覆盖。
5. 复跑凭据相关回归与硬编码扫描。

**验收标准**
- 硬编码检查：FAIL = 0 且 WARN = 0。
- 登录链路 `verify-p1-login.py` 43/43 通过。
- 使用旧密钥签发的 token 全部返回 401；新密钥登录正常。
- 目标环境启动日志中无“默认口令/默认密钥”告警。

**证据回填**：`RELEASE-GATE.md` A9、D1 改为 PASS，附扫描输出摘要；`docs/LAUNCH-CHECKLIST.md` A1 勾选。

**依赖**：无。必须在 M3 之前完成，避免 HTTPS 上线后仍使用旧密钥。

---

### M2 · 配置告警通道并验证可达

**对应**：R2、门禁 D2

**动作**
1. 在 Alertmanager 配置真实接收端（邮件或 webhook），禁止 `receiver: null`。
2. 保留并复核 `ALERTMANAGER_ENV=prod` 下的 fail-closed 行为：缺少接收端时必须拒绝启动。
3. 用一条测试告警（非真实业务故障）验证路由、分组、静默与恢复通知。
4. 复核 12 条规则的阈值来源，把仍引用“本机基线”的项标注为“待 M5 后重标”。

**验收标准**
- 测试告警从触发到接收端可见 ≤ 90 秒，恢复通知同样可达。
- 删除接收端配置后，Alertmanager 启动失败（fail-closed 生效）。
- `promtool check rules` 仍为 SUCCESS。

**证据回填**：`RELEASE-GATE.md` D2 → PASS，记录测试告警名称与接收时间；`docs/review/B-05-VERIFY.md` 追加本次结论。

**依赖**：M1（接收端凭据不得使用旧值）。

---

### M3 · 启用全站 HTTPS 与大流量 SSE 验证

**对应**：R3、门禁 D3

**动作**
1. 在反向代理层配置证书与 80→443 跳转，启用 HSTS；证书与私钥不入库。
2. 为 SSE / WebSocket 路径关闭代理缓冲、放宽读超时，保持逐字输出。
3. 将前端所有 API 基址、WebSocket 地址改为同源相对路径或 HTTPS 地址，消除混合内容。
4. 复跑三浏览器兼容矩阵与关键路径 E2E，重点观察登录、判题进度、AI 点评流式输出。

**验收标准**
- 浏览器控制台无混合内容告警；HTTP 请求全部 301/308 到 HTTPS。
- SSE 逐字输出正常，单条点评不因代理缓冲而整段延迟。
- 三浏览器 15/15、E2E 8/8 通过。

**证据回填**：`RELEASE-GATE.md` D3 → PASS；`docs/compat/COMPAT-MATRIX-20261107.md` 追加 HTTPS 复测结论（不覆盖原记录）。

**依赖**：M1、M2。

---

### M4 · 判题容量决策并固化配置

**对应**：R4、门禁 D4 / B6

**动作**
1. 由技术负责人书面选择其一：
   - **方案 A（接受现容量）**：明确单实例 0.95 题/s、3 实例 0.96 题/s 为当前上限；设定队列积压告警与限流阈值；对外不承诺更高吞吐。
   - **方案 B（优化）**：减少每题容器数、复用判题沙箱或按 CPU 核算调整 `CJ_MQ_CONSUME_THREADS`；每实例线程数 × 实例数不得超过可用核数。
2. 无论选哪种，都必须固化“实例数 × 消费线程数 ≤ CPU 核数”的配置约束，并在部署模板中写明容量公式。
3. 复跑 150 条提交的判题吞吐测试，确认 25/25 AC、无误判 TLE。

**验收标准**
- 决策记录写入 `docs/PERF.md` §3.7 与 SLO 文档，含选定方案、配置值与不承诺范围。
- 判题回归 25/25 AC；3 实例吞吐不低于决策记录中的基线。
- 队列积压有对应告警规则（若无则在 M2 的规则集中补充）。

**证据回填**：`RELEASE-GATE.md` B6、D4 → PASS；`docs/PERF.md` 增加“容量决策”小节。

**依赖**：M2（新增告警需要通道）。

## 4. P1 整改项（受控内测前）

### M5 · 独立压测机复测与告警阈值重标

**动作**
1. 按 `perf-test/RUNBOOK.md` 在第二台机器复跑 `throughput`、`soak` 与判题吞吐，记录机器配置、网络拓扑与客户端资源占用。
2. 对比两轮结果，给出“下界 / 参考值 / 保守容量”三档结论。
3. 用新基线重标 `deploy/monitoring/prometheus/rules/codejudge-alerts.yml` 中的 P95 与错误率阈值，删除仅适用于本机的注释口径。

**验收标准**
- 两机结果与差异原因写入 `docs/PERF.md`，明确哪些数字可用于对外。
- 告警阈值更新后 `promtool` 通过，且不再引用本机基线。

**证据回填**：`RELEASE-GATE.md` B7 → PASS；`QUALITY-SUMMARY.md` §6 的对外表述同步收紧或放宽。

### M6 · refresh token 轮换与吊销

**动作**
1. 设计：refresh token 携带 `jti`；服务端以 `refresh:{userId}` 维护当前有效 `jti` 与版本号，TTL 与 token 有效期一致。
2. 刷新即轮换：旧 `jti` 立即失效；重复使用旧 token 视为重放，撤销该用户全部 refresh token。
3. 在登出、改密、禁用、改角色四个入口调用撤销。
4. 网关与刷新端点继续强制 `type` 校验，不改变 access token 语义。

**验收标准**
- 新增回归断言：登出后刷新返回 401；旧 refresh 重放返回 401 且该用户其他会话失效；改密后旧 refresh 失效。
- 原有登录 43/43、鉴权 56/0 不回归。
- `docs/API-REFERENCE.md` 更新刷新与登出契约。

**证据回填**：`DEFECTS.md` “暂缓-1”改为已修复并附验证；`RELEASE-GATE.md` 无需新增行，但在 A6 备注吊销覆盖。

### M7 · AI 评测引入人类金标准（或明确放弃）

**动作（二选一，必须落文档）**
- **方案 A（引入）**：从现有 40 条样本中抽 30 条，由 2 名评审独立按现有 rubric 打分，计算一致率与加权 kappa，报告与 LLM judge 的差异；坏例重新归类。
- **方案 B（放弃并声明）**：在评测报告与对外材料中明确“仅内部回归基线，不代表人类判断准确率”，并从简历/介绍中删除任何“准确率”表述。

**验收标准**
- 方案 A：产出带标注人、分歧处理规则、κ 值的评测报告；`TEST-REPORT.md` §5 更新结论。
- 方案 B：`QUALITY-SUMMARY.md` §6 与 `docs/ai-eval/report-20261110.md` 口径一致，无“准确率 4.07/5”类表述。

**证据回填**：`TEST-REPORT.md` §5、`QUALITY-SUMMARY.md` §3/§6。

### M8 · 关闭剩余可测性缺口

**动作**
1. 以 `docs/review/TESTABILITY-REVIEW-20261107.md` 附录为清单，优先处理后端可测性中危项（重点：自调用失效、事务边界、外部调用超时、幂等键）。
2. 每项补一条可执行验证（脚本或单测），不接受“看代码确认”。
3. 对暂不修复项写明理由、影响面与触发条件。

**验收标准**
- 20 项待办逐项标记“已修复并验证 / 明确不修（附理由）”，无“待定”。
- 新增验证并入 CI 或 `verify-p6.py`，避免只跑一次。

**证据回填**：`TEST-REPORT.md` §3 可测性行、`RELEASE-GATE.md` A8 备注。

## 5. P2 整改项（发布后迭代）

### M9 · 依赖与静态扫描转为阻断

**动作**：先在报告模式下清零高风险依赖与 SpotBugs 高危项，再移除 CI 中的“失败也继续”逻辑；对确实无法升级的依赖写入豁免清单并注明原因与到期复核点。

**验收标准**：CI 在存在高危时失败；豁免清单有条目上限与复核日期。

### M10 · 生产关闭接口文档

**动作**：生产置 `CJ_SPRINGDOC_ENABLED=false`、`CJ_DOC_WHITELIST_ENABLED=false`；验证 `/doc.html`、`/v3/api-docs` 返回 404；将这两项加入 M1 的生产配置核对清单。

**验收标准**：匿名访问文档端点 404；接口清单不出现在生产响应中。

### M11 · 日志滚动与磁盘保护

**动作**：为容器设置日志驱动大小上限与轮转；或启用 logrotate。验证高日志量场景下磁盘不持续增长。

**验收标准**：模拟错误风暴后，日志目录占用有上界。

## 6. 执行顺序与依赖

```text
M1 凭据 ──┬─→ M2 告警通道 ──┬─→ M3 HTTPS ──→ 受控内测
          │                  ├─→ M4 容量决策
          │                  └─→ M5 双机压测（P1）
          ├─→ M6 refresh 吊销（P1，可并行）
          └─→ M10 文档关闭（P2）

M8 可测性缺口（P1，与 M5/M6 并行）
M7 AI 金标准（P2，独立）
M9 扫描阻断、M11 日志（P2，发布后）
```

**关键路径**：M1 → M2 → M3。M4 与 M5 可并行，但 M5 未完成前不得对外使用“生产容量”表述。

## 7. 验收与回填规则

1. 每个整改项完成后，在 `RELEASE-GATE.md` 填写：日期、命令、关键输出（脱敏）、执行人角色。
2. 只允许在**复验命令真实通过**后把结论改为 PASS；不得先改文档后补验证。
3. 新增验证脚本必须入库，不能只留在个人终端历史中。
4. 整改过程中若发现新缺陷，按 `DEFECTS.md` 的分级口径登记，不在本计划中口头带过。
5. 全部 P0 完成后，重新生成一次 `QUALITY-SUMMARY.md` 的总体结论。

## 8. 完成定义（DoD）

| 阶段 | 完成条件 |
|---|---|
| 可受控内测 | M1–M4 全部 PASS，`RELEASE-GATE.md` 无 ❌ 阻断项 |
| 可公开发布 | 受控内测条件 + M5、M6、M8 完成，且 `QUALITY-SUMMARY.md` 的风险表无 P0/P1 |
| 质量体系稳定 | M7、M9、M10、M11 完成，CI 具备真实阻断能力 |

## 9. 明确不做

- 不引入 Kubernetes、多活、Service Mesh。
- 不为追求吞吐数字而放宽判题超时或正确性校验。
- 不把同机压测结果包装成生产容量承诺。
- 不为“看起来更完整”而新增未验证的指标或看板。
