# 测试策略与方法

> 本页回答一个问题：这些测试是**怎么设计出来的**，不是结果汇总。
> 数字不在此处重述——需要数字请跳到 [TEST-REPORT.md](../quality/TEST-REPORT.md) 与
> [QUALITY-SUMMARY.md](../quality/QUALITY-SUMMARY.md)，本页只解释方法与被放弃的部分。
> 两仓数据不可互套：zx-learn 的结论见该仓 `docs/quality/`。

## 1. 测试范围怎么划：先划"不测什么"

范围按**被测对象能否被独立判死**划，不按功能清单划。

**测**：11 个 Maven 模块（8 个后端服务 + `judge-common` + `judge-api` + `judge-web`）的单元测试、
接口契约、端到端主链路、性能与容量、AI 点评效果。每一层都能给出一条命令和一份落盘产物。

**明确不测**（写进报告而不是省略）：多机独立压测、生产网络与真实第三方回调、移动端、超过 1 小时的稳定性。
理由只有一个：这些在当前环境里**没有可信的对照物**——同机压测只给下界，第三方回调无法本地复刻，移动端没有目标机型。

**第三类：能做但没做**。这类统一标"阻塞"并写明缺什么（缺运行栈、缺额度、缺第二台机器），
不允许用静态检查冒充运行态通过。判据是：没有本次真实执行输出的条目，一律不算完成。

> 出处：[TEST-REPORT.md](../quality/TEST-REPORT.md) §2（被测对象与环境、不在范围内）；[spec.md](../quality/spec.md) §1.2、§4（可验证边界与回填规则）。

## 2. 五类测试各自怎么设计

### 2.1 功能：以状态迁移为主轴，不以页面为主轴

判题主链路是状态机（提交 → 受理 → 编译 → 执行 → 终态），用例按**状态与迁移**组织，不按页面逐个点。
判断依据：终态有 AC / WA / TLE / CE / RE 五类，任一类缺失就意味着一条分支从未被走到；按页面组织容易五类都点到、但每类只走到胜利路径。

边界值集中在"受理"与"限额"两处（限流、幂等、并发消费线程），因为它们决定系统在压力下的行为，
而不是正常时的行为。

### 2.2 接口：契约先于实现，且契约必须可执行

接口测试的对象是**文档承诺**，不是代码现状。所以先做契约审查：示例里的成功码、字段名、错误事件语义
必须与实现一致，否则测试写出来就是两套真值。审查中发现的同类问题（示例成功码、SSE 字段名、算法描述冲突）
都按"文档缺失"登记，并给出可执行断言。

鉴权按**角色 × 端点**矩阵覆盖，而不是只测"未登录返回 401"——越权与降级的差别就在角色维度上。

### 2.3 兼容：只测会阻断主流程的组合

三浏览器 × 主流程用例，而不是全量功能 × 全浏览器。判断依据：浏览器差异主要落在长连接、SSE 与
WebSocket 的降级行为上，这些恰好都在主流程里；其余页面的样式差异不构成放行风险。

### 2.4 性能：先证明口径成立，再看数字

性能测试的第一步不是加压，是**验证负载模型能不能回答这个问题**。固定工作量的计划（ramp-up 固定、
总量固定）观测到的吞吐有算术上限，用它判"吞吐是否达标"会得出与系统无关的结论，所以这类计划被判为
"不适用"，而不是"不通过"。真正用于判定的是恒定负载、1 小时长稳与判题吞吐三条。

判题吞吐单独测，因为它与 HTTP 吞吐不是同一个瓶颈：瓶颈在每题的容器启停，加实例不涨吞吐。
这条结论直接决定了"接受现容量"，而不是继续堆机器。

### 2.5 AI 效果：把"能不能跑"和"对不对"分开

样本按判题终态分层抽取，保证五类终态都有代表；四维评分中，**可执行性用沙箱真实编译结果判定**，
其余三维才用 LLM 评分。判断依据：可执行性是唯一有客观对照物的维度，若连它也靠模型自评，整份评测就没有锚点。
因此结论只表述为"内部回归基线"，不表述为准确率。

> 出处：[TEST-REPORT.md](../quality/TEST-REPORT.md) §3、§4、§5；[RELEASE-GATE.md](../quality/RELEASE-GATE.md) A1–A8、B1–B5、C1–C4；
> [TESTABILITY-REVIEW-20261107.md](../review/TESTABILITY-REVIEW-20261107.md) §1（契约可测性）。

## 3. 门禁怎么定的

门禁按**"错了会不会被判死"**分组，不按"重要不重要"分组：

- **A 组（代码与测试）/ B 组（性能与容量）**：错了等于系统不可用或给出错误结论，设为阻断。
- **C 组（兼容与体验）**：影响体验但不影响正确性，设为非阻断，但必须登记风险承接人。
- **D 组（生产化动作）**：机制上阻断，但只能由目标环境执行，因此单列一组，不能靠本地证据勾选。

结论列只有 PASS / 有条件 / 未完成三种，**"有条件"不计入通过数**。放行结论里"通过 N 项"的 N，
就是表中结论列为 PASS 的阻断项行数；有条件项再多也不算——否则门禁会退化成"看起来都过了"。

另外两条规则是刻意加的：① 新增告警规则只做了语法校验、没做规则引擎校验时，结论必须写"有条件"，不能写 PASS；
② 已记录决策但复测未执行的项（如容量决策），标"有条件"，并在同一行写出复测条件。

> 出处：[RELEASE-GATE.md](../quality/RELEASE-GATE.md) §1（A/B/C/D 四组）、§2（放行判定）；[TEST-REPORT.md](../quality/TEST-REPORT.md) §1。

## 4. 风险取舍：时间有限时先测什么

排序原则是**"先测错了会让人相信错结论的东西"**，而不是先测功能多的东西。据此的顺序：

1. 数据契约（成功态是否真的有内容、幂等边界）——错一次会污染后续所有评测与展示；
2. 鉴权与发布顺序（换钥、token 契约）——错一次是全站不可用；
3. 可观测性（requestId 跨消息链路）——它决定故障能否被复盘，属"影响力放大项"；
4. 性能与容量——只影响承诺，不影响正确性，且本机只能给下界。

**放弃的部分与代价**（都写进放行单，不隐藏）：
- 放弃独立压测机 → 容量只能表述为下界，不能对外承诺吞吐；
- 放弃人工金标准 → AI 评测只能内部回归，不能对外说准确率；
- 放弃超过 1 小时的长稳与 gVisor → 隔离强度与长期稳定性均为已知风险；
- 放弃生产环境动作 → 凭据、告警通道、HTTPS 一律标未完成，不在地契里"代做"。

> 出处：[TESTABILITY-REVIEW-20261107.md](../review/TESTABILITY-REVIEW-20261107.md) §6（优先级）；[LAUNCH-READINESS.md](../LAUNCH-READINESS.md) §E（已知限制）；
> zx-learn `docs/quality/QUALITY-SUMMARY.md` §4（主要风险）、§5（放行建议）。

## 5. 已知方法局限

1. **同机压测**：负载发生器与被测服务争抢 CPU / 内存 / 网卡，绝对吞吐只是下界，不能当容量承诺。
2. **无人类金标准**：同一 judge 两次同分只能证明可复现，不能证明与人类判断一致。
3. **单机单点**：没有第二台机器，也没有生产网络，跨机网络抖动与代理行为无法复现。
4. **只读审查不等于验证**：可测性审查是"发现 + 建议"，被引用的条目若没有独立验证记录，只能表述为待办。
5. **静态断言不等于运行态通过**：缺运行栈时只能做 grep / YAML / 脚本自测，这类证据必须与实跑证据分开标注。

> 出处：[TEST-REPORT.md](../quality/TEST-REPORT.md) §4.2、§7；[TESTABILITY-REVIEW-20261107.md](../review/TESTABILITY-REVIEW-20261107.md) 闭环状态声明；
> [LAUNCH-READINESS.md](../LAUNCH-READINESS.md) §E。

## 6. 如果重做一次，会改哪三件事

1. **把"可判定口径"前移到设计阶段**：26 项可测性缺口里有 20 项仍待处置，其中"文档缺失"类补文档即可测；
   这类返工本可以在写设计时就避免。
2. **把人工契约改成启动期自检**：换钥顺序、token 契约这类"靠人记"的约束，应在不一致时拒绝启动，
   而不是等线上 401 才发现。
3. **让证据采集与执行同批完成**：演练日志随容器重建丢失、复核时只能重跑，说明"先跑后补证据"不可靠；
   执行即落盘，后来者才能顺着命令复现。

> 出处：[TESTABILITY-REVIEW-20261107.md](../review/TESTABILITY-REVIEW-20261107.md) §0、§6；[E-01-KEY-ROTATION-DRILL.md](../review/E-01-KEY-ROTATION-DRILL.md) 证据声明。
